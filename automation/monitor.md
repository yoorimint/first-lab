# 운영 감시 (2시간마다, 운영자가 그만하라고 할 때까지 — 11/5 '10분 단위로' → 11/8 '30분' → 11/8 '2시간': 공개 대기가 몇 주라 검수가 급하지 않고 배포·보류는 서버가 스스로 풂)

운영·감시를 맡은 Claude 세션이 따르는 문서. 어느 세션이든 이 문서만 읽으면 바로 이어서 할 수 있게 쓴다.
운영 원칙은 저장소 맨 위 `CLAUDE.md`, 운영자 지시 기록은 `automation/operator-notes.md`.

## 시작 (새 세션이 이어받을 때)
1. `CLAUDE.md` → `automation/operator-notes.md` → 이 문서 순서로 읽는다.
2. `send_later` 로 2시간 뒤 감시 예약 (메시지: "2시간 감시 차례: automation/monitor.md 대로 …"). 예약은 그 세션에만 오므로 세션이 바뀌면 새로 건다.
3. 감시 차례마다 아래를 하고, 끝나면 다시 2시간 예약 (차례 시작하자마자 먼저 예약). 새 글이 여러 편이면 외부 검수를 동시에. 차례마다 매번 할 일: 배포 상태·/health·봇 기록 오류·patch_problems·보류 글. 새 글 표본 검수·보완 작업은 이어서 하되 끝나면 바로 다음 예약.

## 감시 차례마다
- **애드센스 승인 보고를 받으면 (운영자 11/9)**: 그날 애드센스↔GA4 연결·글별 수익 기록(1번)을 만들고, 그 수익으로 '수익이 꾸준한 글'도 보강·제목 바꾸기에서 빼는 기준을 bot/refresh.is_strong 에 더하고(운영자 11/11 '돈이 꾸준히 들어오는 글도 있을 거 아냐'), send_later 로 **6개월 뒤**(운영자 11/11 '승인 나고 6개월 정도는 지켜봐야') '잘 되는 글 구조·카테고리·키워드를 글감에 반영할지(2번) 운영자에게 묻기' 예약 — 수익 기록과 '수익 꾸준한 글 보호'는 승인 날부터(보호는 수정을 안 하는 것이라 일찍 해도 손해 없음), 글감·글쓰기 지시를 바꾸는 판단만 6개월 뒤. 미리 만들지 않음 (operator-notes.md).
- **치명적 실수는 즉시 (운영자 11/9)**: 사이트 화면에 보이는 잘못(엉뚱한 링크·계산기, 틀린 숫자, 깨진 화면)은 찾은 그 차례에 고치고 올린 뒤, 배포 끝나는 대로 실제 화면을 바로 열어 확인·보고. '다음 점검 때 확인'으로 미루지 않음. 확인 전엔 원인을 짐작으로 말하지 않음.
0. **새 초안은 전부 직접 읽기 (운영자 11/11, 12/5까지)**: 1번에서 나온 '검수 필요' 새 글은 표본이 아니라 전부 — 감시 세션이 본문을 처음부터 끝까지 직접 읽고(계산 예시는 손으로 다시 계산, 계산기가 있으면 defs·data 코드도 직접 끝까지 — 운영자 11/11 '계속 그렇게 해라') 외부 검수와 대조, 고친 뒤 reviewed.txt. 놓친 유형은 검사·테스트로.
1. **검수할 글 찾기**: `git pull` 후 `python3 automation/unreviewed.py` — 서버의 공개 대기·보류 글 전체를 글 번호로 `automation/reviewed.txt` 와 대조해, 검수 안 된 글과 최신 본문 파일(보류 수정본 우선)을 알려 준다. **시각 기준으로 새 글을 찾지 않는다** (경계에 걸린 #163 이 빠진 적 있음).
2. **외부 검수** — 11/5부터 대기 글 검수는 글쓰기 작업이 직접 한다(/next `review_target`, daily-writer.md). 감시 세션은 같은 글을 따로 고치지 않는다(patches.json 충돌).
   감시 세션 몫: 글쓰기 작업이 검수한 글(`reviewdone-*.json`) 중 1~2편을 표본으로 아래 절차대로 다시 검수해, 글쓰기 작업이 놓친 것은 고치고 **놓친 유형을 관문·검사로** 옮긴다.
   (아래는 그 표본 검수와, 글쓰기 작업이 못 하는 경우의 절차)
   - `automation/review-prompt.md` 로 서브에이전트 검수. 3~4편씩 묶어 병렬, **model 은 "opus" 로 직접 지정**.
   - **계산기가 들어간 글**(본문에 `[firstlab_calc id="…"]`)은 그 계산기 파일(`wordpress/themes/first-lab/calculators/defs/<id>.js`, `tests/<id>.json`)도 검수자에게 같이 준다 — 검증 사례 정답이 계산기와 같은 착각으로 만들어지면 테스트가 못 잡음 (11/4 상속세 계산기: 배우자공제 한도에서 장례비를 뺀 오류).
   - 검수 결과는 **내가 한 번 더 훑어본다**: 근거 링크가 실제로 그 말을 하는지, '주장' 원문이 글에 그대로 있는지, 수정안이 더 틀리지 않았는지.
   - **'찾지 못함'은 '없음'이 아니다**: 사이트 메뉴·기능·제도가 '확인불가'면 내가 직접 한 번 더 찾아본다(WebFetch). 그래도 안 되면 '없다/못 찾았다'고 단정하는 수정안은 쓰지 않고 '○○에서 확인해 보세요'로만 완화한다 (11/4 #219 파인 대출 계산기를 없다고 잘못 고친 일).
   - 확인불가는 글쓴이가 남긴 근거 링크(`wordpress/queue/<글>.json` 의 review 항목 urls)를 내가 열어 다시 본다 — 검수자는 그 링크를 일부러 안 믿게 했기 때문 (11/5 #477 응시료: 큐넷 상세 페이지에서 확인됨).
   - **'틀림'으로 고칠 때는 근거 원문을 내가 직접 열어 확인한 뒤에만** 고친다 (검수자와 나는 같은 계열 모델이라 같은 착각을 할 수 있음). 못 열면 '틀림' 수정 대신 확인처 안내로 완화.
   - **고친 것마다 오류 유형(`"type"`)을 붙인다** — `automation/error_types.json` 에 있는 유형. 맞는 유형이 없으면 새 유형과 **막는 방법(코드·테스트, 안 되면 검수로만 잡는 이유)을 먼저 등록**해야 테스트가 통과한다 (11/5 운영자: 고친 모든 것에 재발 방지).
   - 패치를 쓴 뒤 `python3 automation/common_errors.py` 로 '자주 틀린 유형' 확인표를 다시 만든다 (글쓰기 독립 검수자가 읽음, 테스트가 최신인지 확인).
   - **반영은 `python3 automation/apply_review.py <글번호> "<제목>" [패치목록.json]` 로만** — 검사(유형·찾을 문구 1번·고친 문구에 안 남음) 통과해야 저장하고, 저장한 뒤에만 검수 완료 기록 (11/5 #542 순서 실수).
   - 고치기: `wordpress/patches.json` (post, why, find, replace_paragraph, tag p/li/tr). find 문구는 고친 뒤에 남으면 안 됨 (테스트가 막음). 패치마다 `prevention` 필수 (check:<검사> 또는 review_only:<이유>, apply_review 가 막음) — review_only 가 automation/review-only-log.md 에 같은 꼴로 2번 쌓이면 검사로 옮긴다.
   - 같은 종류 오류가 2편 이상이면 → 글쓰기 단계(검수 관문 `bot/review_gate.py`, 지시서 `automation/daily-writer.md`)를 **코드로** 보강.
   - **계산기 따로 확인**: `unreviewed.py` 끝의 '계산기 검수 필요' 목록도 전부 검수 (글이 먼저 검수된 뒤 계산기만 추가되는 경우가 있음, 11/5 공인중개사 점수 계산기). 검수·수정 뒤 `calc:<이름>` 줄을 reviewed.txt 에 추가.
   - 검수한 **글 번호**를 `automation/reviewed.txt` 에 추가해 커밋 (`번호 제목`). 수정 패치를 실제로 써넣은 **다음에만** 추가한다 (패치 검사에 걸려 수정이 저장 안 됐는데 검수 완료로 기록된 적 있음, 11/5 #416).
   - **근거 대조 정확도 재기 (11/5~, 며칠)**: `unreviewed.py` 가 보여 주는 서버 근거 대조('페이지에 없음' 주장)와 외부 검수의 틀림·확인불가를 비교해 `automation/source-check-log.md` 에 한 줄씩 (글 번호, 대조 없음 N, 그중 검수도 문제 삼은 것 M, 검수만 찾은 것 K). 오탐이 적으면 관문 보류에 쓰도록 운영자에게 보고.
   - **글쓰기 세션이 오류표를 실제로 읽는지**: 봇 기록의 최근 '연속 작성 N번째' 세션 주소(cse_XXX → session_XXX)를 `list_events` 로 열어 `common-errors` 를 읽었는지·하위 검수자에게 줬는지 확인. 안 읽었으면 지시서 문구를 고친다.
   - **법령 감시** (`/maintenance` 의 law_watch): 곧 시행될 개정이 글쓰기에 넘어가는지, 입법예고(확정 아님) 중 우리 글 핵심을 바꿀 만한 것이 있는지 본다 — 확정되면 감시가 시행 예정으로 잡는다.
3. **글 품질 훑기**: 제목 숫자가 본문에 있는지, 같은 문장 반복, 어색한 문장, 계산 제목은 다시 계산.
   - 배포 뒤 `python3 automation/verify_patches.py` — 고친 내용이 서버 글에 실제로 들어갔는지 전수 확인 (종료코드 1 이면 원인 찾기).
4. **서버 상태** (읽기 API `/wp-json/firstlab/v1/maintenance`, 헤더 X-Firstlab-Token):
   - 봇 기록의 오류, 연속 작성 자동 정지, 보류 초안(이유가 진짜인지 관문 오탐인지), 예약 공개.
   - 색인 (`index`, bot/index_check): 공개 14일 지난 글 색인률이 80% 이상으로 2주 이어지면 운영자에게 하루 공개 편수를 3편으로 늘릴지 묻는다. 미색인 사유가 '읽어 갔지만 색인 안 함'으로 쌓이면 그 글들 품질부터 본다.
   - 배포: `curl -s https://first-lab.kr/deployed-version.txt` 가 main 과 다르면 15분 따라잡기(deploy.yml schedule)가 도는지.
   - 배포 기록의 `[대표 사진] 요약: 사진 N · 대기 M · 없음 K` — K 가 늘면 원인 확인.
   - 사진: 한도(하루 약 50장, 오전 9시 초기화) 소진 시 '대기' 로 넘어가는지, 오전 9시 이후 '사진 채우기' 로 채워지는지.
5. **문제를 찾으면**: 지금 것 바로잡기 + 재발 방지(코드·테스트) → 테스트 종료코드 확인 → main 에 올림 → 배포 확인.
   - 테스트는 **root 가 아닌 사용자로** 돌린다 (GitHub 검사와 같게): `useradd -M ci 2>/dev/null; runuser -u ci -- env HOME=/tmp python3 -B -m unittest discover -s tests`
     — 11/5 감시 세션(root)에선 통과했는데 검사 환경은 /var/lib 권한이 없어 실패, 배포가 1시간 멈춤.
6. 운영자에게는 한글로, 바뀐 것과 결과만 짧게.

## 12/5 까지 (운영자 11/5): 작성자는 새 글만, 대기 글 외부 검수는 감시 세션
